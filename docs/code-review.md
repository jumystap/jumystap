# Рекомендации по код-ревью

Как проводить ревью ветки перед мёрджем. Роль ревьюера — старший разработчик: по делу, без воды, только по диффу.

## Как снять изменения

Базовая ветка — `master` (ветки `dev` в репозитории нет).

```bash
git log master..HEAD --oneline        # контекст коммитов
git diff master...HEAD --stat         # какие файлы затронуты
git diff master...HEAD                # сами изменения — ревью по ним
git status --short                    # untracked/staged мусор, который случайно попадёт в коммит
```

Ревьюим только дифф. В неизменённый код заглядываем, только чтобы понять контекст. Если дыра pre-existing, но дифф усиливает её последствия — флагуем с пометкой «корень pre-existing».

## Классификация находок

- **[Блокер]** — нельзя мёрджить: баг, дыра в безопасности, потеря/утечка данных.
- **[Важно]** — исправить до мёрджа.
- **[Мелочь]** — некритично, можно поправить следом.
- **[Идея]** — на подумать. Не уверен в проблеме — это [Идея]/вопрос, а не баг.

Формат находки: `файл:строка` → что не так → почему это проблема → как починить (с кодом, где уместно). Сначала итог в 1–2 строки: готово к мёрджу / есть блокеры / нужны правки.

## Чек-лист

**Гигиена репозитория (проверять первым делом!)**
- В индексе нет дампов БД, экспортов и прочего мусора (`git status --short`). Реальные прецеденты в этом проекте: `backup.sql` на 938 МБ с ПДн и токеном бота, `ad_categories.sql` на 3.8 млн строк. Корневые `*.sql` уже в `.gitignore` — не обходить его.
- Привычка `git add .` — главный источник таких утечек. Добавлять файлы поимённо.
- Новые нужные файлы не забыты в untracked (`??`) — иначе они не попадут в мёрдж.

**Безопасность**
- **Никаких токенов/секретов во фронтенде** (`resources/js`) и в коммитах. Прецедент: токен Telegram-бота был захардкожен в `FeedbackModal`/`ScamModal` — любые внешние отправки только через бекенд-эндпоинт.
- **Ownership-проверки**: в проекте нет Policy — в каждом экшене с `{id}`/model binding, который меняет или показывает приватное, проверять `$model->user_id !== Auth::id()` → `abort(403)`. Прецедент: `PUT/DELETE /resumes/{id}` позволяли править и удалять чужие резюме.
- **Видимость контента со статусами**: новые выборки из `user_resumes` / `announcements` / `ads` фильтровать по статусу публикации. Проверять ВСЕ точки выхода: детальные страницы, списки, поиск, фильтры, сортировки, подзапросы (`whereExists`), PDF/выгрузки.
- Новые публичные POST-эндпоинты — с `throttle` (спам/abuse).
- Пользовательский ввод, попадающий в HTML-сообщения (Telegram parse_mode HTML) — экранировать.
- Mass assignment: `$fillable` не должен позволять клиенту задавать статусы/служебные поля; статус выставляется кодом, а не из запроса.

**Внешние вызовы (Telegram/SMS/Bitrix)**
- `try/catch` + `Log::error` с контекстом. Помнить: `catch (\Exception)` не ловит `TypeError` — если аргументы могут быть null (не заданный env), нужен guard на конфиг до вызова или `catch (\Throwable)`.
- Синхронные внешние вызовы в HTTP-запросе — красный флаг: таймаут 30с у Telegraph подвешивает запрос. Несколько вызовов подряд — только в очередь (queue-контейнер в docker-compose уже работает).
- Конфиг внешних сервисов — через `config/services.php` + env, не хардкодом в коде.

**Laravel-практики проекта**
- Слои: Controller (тонкий) → Service (логика) → Repository (запросы) → Model. Валидация в FormRequest. Никаких новых слоёв (Resources/Policies/Events/DTO) — см. `DEVELOPMENT_RULES.md`.
- Транзакции вокруг многошаговых записей (родитель + дети + история).
- Статусы — через enum в `app/Enums` с `label()/color()`; история смен статуса — отдельной таблицей (образец: `ad_status_histories`).
- Админка — **Blade/AdminLTE** (`resources/views/admin/*`), не React. React-страницы `Pages/Admin/*` — легаси.
- i18n: новые строки в **оба** файла локалей `public/locales/ru` и `public/locales/kz`.

**Миграции**
- `down()` обратим; backfill существующих данных при добавлении статусов (grandfathering), чтобы живой контент не пропал.
- Индексы на новые FK и часто фильтруемые колонки; для подзапросов вида `user_id + status` — составной индекс.
- Помнить: миграции содержат MySQL-специфику (префиксные индексы) — на sqlite не проверять.

**Тесты**
- Новая логика покрыта Pest-тестами: Feature (HTTP/доступы) + Unit (сервисы). Негативные кейсы доступа обязательны (чужой → 403, гость → 404).
- Как гонять локально — см. `docs/qa.md`, раздел «Локальный запуск». Хост-PHP нет, стандартная `UserFactory` несовместима со схемой (`email_verified_at`, обязательный `role_id`) — использовать `makeUser()` / `createUserResume()` из `tests/Pest.php`.
- Telegram в тестах — `Telegraph::fake()`; для отправок нужен бот в `telegraph_bots` (создавать в тесте).

**Чистота**
- Нет `dd()/dump()/console.log`, закомментированного и мёртвого кода (прецедент: `UserResumeController::index()` без роута, отдающий все резюме).
- Повторное ревью после правок обязательно: проверять и сами фиксы (они тоже ломаются), и не появился ли новый мусор в индексе.
